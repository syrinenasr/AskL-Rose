The failure labels

Each failure gets exactly one label: the first thing that went wrong.

gate

A data question was refused: the model set is_data_question to false and wrote no SQL. Example: q09 "How many customers are registered?"

invented column

The SQL uses a column that doesn't exist in that table, so SQL Server returns "Invalid column name" and the repair didn't fix it. Example: q03 SalesPersonKey instead of EmployeeKey.

wrong logic

The SQL runs but answers a different question: wrong join, wrong aggregation, wrong filter or wrong column. Example: q23 averages order lines instead of orders.

T-SQL syntax

Syntax from another SQL dialect that SQL Server rejects. Here always FETCH FIRST without OFFSET (PostgreSQL style) instead of TOP n.

SCD

Slowly Changing Dimension. Ignored the history rows of such a dimension: DimProduct and DimEmployee keep old versions, and "current" needs Status = 'Current'. Example: q08.

question design

Our fault, not the model's: the question is ambiguous, hides a tie, or the grader is too strict. No failure carries this label any more: the grader fixes below removed them (q16 was reworded and now fails on the model's logic; q36 passes with the tolerance).

The five steps

Every failure from the run with the semantic layer went through the same five steps.

  1. Read the reason run.py gave: an SQL error, "treated as not a data question", a wrong row count, or "no column matches" (different values).
  2. Compare the SQL: the model's query next to the reference in eval/questions.yaml, looking for the first difference.
  3. Run both against the database and compare the actual numbers.
  4. Decide whose fault it is: the model's, or ours (an ambiguous question, a tie, a rounding difference).
  5. Give it one cause label, so failures can be counted.

The 34 questions that don't flip are 18 + 16. The 18 that pass both times are simple questions, single joins the model handles alone, and the 5 non-data questions: they didn't need the layer. The 16 that fail both times weren't saved by it: invented columns, wrong logic, FETCH FIRST, the gate, and q16's ignored tie.

The flips matter most because the semantic layer is the only thing that changed between the two runs: same model, same questions, same settings. When a question flips, the layer (or chance) made the difference. The 34 questions that don't flip say nothing about the layer: they were easy enough without it, or too hard even with it.

13 questions pass only with the semantic layer and 3 pass only without it, a net gain of +10. In 10 of the 13, the model used a definition from the layer; 3 flipped for no clear reason (the model is a bit random, since a different prompt leads to different SQL). q01 and q38 used to be counted here: they were our grader's fault and now pass both times.

Conclusion

The conclusion answers these questions from the tables above.

  • Does the semantic layer help? By how much (31 vs 21)?
  • Where does it help: which tags, and through which definitions (see the flips)?
  • Where does it hurt, and why might a longer prompt make the gate refuse simple questions?
  • Of the 19 model failures, which are general problems (gate, invented columns, FETCH FIRST, ignored ties) and which are one-off (helmets as a product name)?
  • Which failures could the semantic layer fix with a new definition (order value, current product, current employee, loyal customer), and which need a prompt or code change?
  • What is the first fix, and which questions are re-run to check it?
